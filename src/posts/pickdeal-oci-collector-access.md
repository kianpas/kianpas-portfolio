## 기능을 붙이기 전에 막힌 수집

픽딜은 여러 커뮤니티의 핫딜을 모아 보는 개인 프로젝트다. 프론트엔드는 Vercel에, Spring Boot 백엔드와 PostgreSQL은 OCI에 올렸다. 수집기는 백엔드 안에서 주기적으로 HTML을 가져와 제목, 가격, 판매처 등을 정리하고 저장하는 구조였다.

처음에는 출처를 늘리는 일이 주로 HTML 파서를 추가하는 작업일 거라고 생각했다. 사이트마다 게시판 구조가 다르니 그 부분만 맞추면 될 것 같았다. 그런데 실제로는 HTML을 읽는 단계까지 가지 못하는 경우가 먼저 나왔다.

퀘이사존은 운영 수집 로그가 찍혔지만, 루리웹은 연결 시간이 초과됐다. 뽐뿌를 추가하려고 확인하니 이번에는 `403 Forbidden`이 돌아왔다. 로컬 브라우저에서는 잘 열리는 게시판이라 더 헷갈렸다.

## HTTP 수집이어서 안 되는 걸까

기존 수집기는 Java의 Jsoup을 사용한다. `Jsoup.connect()`로 페이지를 요청하고, 받은 HTML에서 필요한 항목을 추출한다. 브라우저를 띄우지 않기 때문에 구조가 단순하고 자원 부담도 작다.

여기서 말하는 HTTP 수집은 암호화되지 않은 `http://` 접속을 뜻하는 것이 아니다. 실제 요청 주소는 처음부터 `https://`였다. 뽐뿌의 403은 HTTPS 연결에 실패한 것이 아니라, 연결 후 요청이 거부된 결과였다.

루리웹은 양상이 달랐다. OCI에서 DNS 조회는 됐지만 TCP 443 연결부터 시간 초과가 발생했다. 개인 PC에서는 같은 주소에 curl로 요청해도 200이 나왔다. 서버의 방화벽과 OCI Egress 규칙도 확인했지만 해당 연결을 막는 규칙은 찾지 못했다.

뽐뿌의 403과 루리웹의 연결 실패를 같은 문제라고 단정할 수는 없었다. 다만 둘 다 실행 위치에 따라 결과가 달랐다.

## curl 결과만으로 판단하면 안 됐다

처음에는 curl로 접근이 되는지부터 확인했다. 빠르고 간단한 진단 방법이지만, 이것을 실제 수집기와 같은 조건이라고 보면 안 됐다.

퀘이사존도 curl에는 Cloudflare 검증 페이지를 반환했다. 그런데 그보다 앞선 운영 수집 로그에는 30건을 처리한 기록이 있었다. 두 요청의 시점은 달랐지만, 적어도 curl의 403만 보고 수집기까지 불가능하다고 결론 내릴 수는 없었다.

그래서 기존 `HtmlFetcher`를 그대로 호출하는 일회성 진단 도구를 만들었다. Spring과 DB는 시작하지 않고, 목록만 요청한 뒤 종료하도록 했다. 수집 성공 여부를 확인하려다 운영 데이터를 바꾸거나 스케줄러를 중복 실행하지 않기 위해서였다.

이 방식으로 OCI에서 뽐뿌에 요청해도 403이 나왔다. 그제야 기존 Java 수집 방식에서도 접근이 거부된다는 사실을 확인할 수 있었다.

## 도구를 바꿔 보고, 실행 환경도 맞춰 봤다

브라우저 자동화도 비교했다. 개인 PC의 시크릿 창에서는 게시판이 바로 열렸고, 쿠키 없는 새 세션의 Playwright도 창을 띄운 실행에서는 실제 목록을 받았다. 반면 앞서 실행한 headless 테스트는 403이었다. 시간 차이가 있는 실험이므로 창의 유무만이 원인이라고 확정하지는 않았다.

다른 공개 핫딜 프로젝트의 구현도 살펴봤다. 브라우저를 실행하는 방식뿐 아니라, 브라우저의 통신 특성을 모방하는 HTTP 클라이언트를 사용하는 사례가 있었다. Java에서도 비슷한 기능을 제공하는 `impersonator`를 찾았다.

이번에도 운영 수집기를 바로 교체하지 않았다. 별도의 진단 프로젝트에서 고정된 프로필로 한 번만 요청하도록 만들었다. 인증서 검증은 유지했고, 프록시나 기존 쿠키를 가져오지 않았다. 재시도와 리디렉션도 껐다. 이 실험은 요청 방식의 차이를 확인하기 위한 것이지, 성공할 때까지 설정을 바꿔 가며 반복하는 수집기는 아니었다.

결과는 다음과 같았다.

| 실행 환경 | 요청 방식 | 결과 |
| --- | --- | --- |
| 로컬 PC | Java impersonator | 200, 게시글 링크 후보 42개 |
| OCI | Java impersonator 진단 컨테이너 | 두 번 모두 403 |
| 로컬 Docker Desktop | 같은 진단 코드와 Dockerfile | 200, 게시글 링크 후보 42개 |
| OCI | RSS 주소에 일반 curl 요청 | 403 |

42개는 중복을 제거한 게시글 링크 후보 수다. 실제 딜을 42건 저장했다거나 최신 데이터 전체를 검증했다는 뜻은 아니다.

로컬 Docker에서도 성공하면서 단순히 Docker를 썼기 때문에 실패한 것은 아니라는 근거가 생겼다. 같은 코드가 집에서는 되고 OCI에서는 안 되니, 출발 IP나 네트워크 환경에 따른 제한 가능성이 커졌다.

다만 여기서도 “OCI 전체 IP 대역이 차단됐다”고 확정하지는 않았다. 두 환경의 CPU 아키텍처와 이미지 세부 조건까지 완전히 같지는 않았고, 사이트 측의 차단 규칙을 확인한 것도 아니었다. 확인된 것은 **현재 내 OCI 환경에서는 거부되고, 로컬 환경에서는 성공한다**는 점이었다.

## 코드 수정 대신 수집 위치를 나누기로 했다

이 시점부터는 파서를 더 만드는 것으로 해결할 문제가 아니었다. 그렇다고 포트폴리오용 프로젝트에서 접근이 될 때까지 서버나 라이브러리를 계속 바꾸는 것도 맞지 않아 보였다.

그래서 수집은 노트북 같은 로컬 기기에서 하고, 데이터 저장과 조회는 기존 클라우드에 남기는 방향을 선택했다.

```text
로컬 기기
  목록 수집 · 필요한 상세 조회 · 데이터 정규화
                │
                │ 인증된 HTTPS 전송
                ▼
OCI
  백엔드 API · 중복 확인 · 그룹화 · PostgreSQL
                ▲
                │ 조회 API
                │
Vercel 프론트엔드
  사용자는 기존처럼 웹에서 조회
```

수집할 때 로컬에서 필요한 일을 하고 결과만 서버에 보내는 구조다. 방문자의 브라우저가 대신 수집하는 것은 아니다. DB를 외부에 직접 노출할 필요도 없다.

로컬 기기가 꺼져도 OCI에 저장된 데이터는 남는다. 화면은 계속 볼 수 있고 새 데이터의 수집만 멈춘다. 수집이 멈춘 것을 사용자가 알 수 있도록 마지막 수집 시각을 보여 주는 것도 함께 고려하고 있다.

단, **이 글을 쓰는 시점에 완료한 것은 진단 도구와 접근 비교까지다. 로컬 수집 결과를 OCI로 전송하는 구조는 채택한 방향이며 아직 구현 전이다.** 로컬에서 모든 출처의 전체 수집 과정이 검증된 것도 아니다. 뽐뿌는 목록 링크 후보를 확인했고, 루리웹은 일반 HTTP 요청 성공까지 확인했다.

## 개인 프로젝트에 맞는 선을 정했다

처음에는 노트북을 계속 켜 둬야 하나 싶었다. 하지만 픽딜은 실시간성을 보장해야 하는 상용 서비스가 아니라 포트폴리오이자 개인용 프로젝트다. 수집 하나 때문에 노트북을 24시간 켜 두거나 별도 장비부터 살 필요는 없다고 판단했다.

우선은 로컬 기기를 사용하는 동안만 수집하는 정도로 시작하려 한다. 꺼져 있는 사이 목록에서 밀려난 글은 놓칠 수 있다. 다시 켰을 때 모든 글을 복구하는 기능까지 한꺼번에 만들지는 않을 생각이다. 기존 bootstrap 설정이 있다고 해서 중단 구간이 자동으로 복구된다고 가정해서도 안 된다.

대신 실제 분리 작업에서는 몇 가지를 챙겨야 한다.

- 로컬 수집기는 DB 없이 기동할 수 있어야 한다.
- 신규 글만 상세 조회하려면 이미 저장된 외부 ID를 서버에 묶어서 확인하는 절차가 필요하다.
- 수신 API에는 인증과 입력 검증을 두고, 기존 공개 쓰기 제한은 유지해야 한다.
- 전송 결과를 받지 못해 다시 보내더라도 중복 저장되지 않아야 한다.
- 전송 실패 시 재전송 범위와 데이터 유실 가능성을 명확히 정해야 한다.

같은 JAR를 역할별 프로파일로 실행하는 방법도 가능하지만, 현재 DB에 의존하는 수집 흐름을 분리하는 작업은 필요하다. 스케줄러 설정 한 줄만 바꾸면 끝나는 일은 아니다.

## 이번에 남긴 기준

이번 문제에서 가장 크게 배운 점은 **HTML 파싱 가능성과 운영 서버에서의 접근 가능성은 별개**라는 것이다. 로컬에서 페이지가 열린다는 이유만으로 배포 환경에서도 수집할 수 있을 것이라고 생각하면 안 됐다.

다음 출처를 추가할 때는 접근 정책과 제공 피드를 먼저 확인하고, 실제로 실행할 환경에서 작은 진단부터 할 생각이다. 성공 여부를 판단할 때도 상태 코드, 실제 목록 수신, 파싱, 저장을 나눠서 봐야 한다.

로컬 수집으로 방향을 정했다고 해서 사이트의 접근 제한이나 재사용 조건이 사라지는 것은 아니다. 개인용이라는 이유로 자동 수집이 무조건 허용되는 것도 아니다. 공개 화면에 내보낼 데이터 범위와 사이트 정책은 별도로 확인해야 한다.

이번 선택은 클라우드 접근 문제 자체를 고쳤다는 의미보다는, 내 프로젝트의 목적에 맞게 책임을 나누기로 한 결정에 가깝다. 실시간으로 모든 딜을 놓치지 않는 것보다, 수집이 중단돼도 이미 모은 데이터를 볼 수 있는 구조부터 만드는 편이 지금은 더 적절하다고 봤다.
