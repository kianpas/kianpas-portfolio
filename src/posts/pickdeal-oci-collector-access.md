## 기능을 붙이기 전에 막힌 수집

픽딜은 여러 커뮤니티의 핫딜을 모아 보는 개인 프로젝트다. 프론트엔드는 Vercel에, Spring Boot 백엔드와 PostgreSQL은 OCI에 올렸다. 수집기는 백엔드 안에서 주기적으로 HTML을 가져와 제목, 가격, 판매처 등을 정리해 저장한다.

처음에는 출처를 늘리는 일이 HTML 파서를 하나씩 붙이는 작업일 거라고 생각했다. 사이트마다 게시판 구조가 다르니 그것만 맞추면 될 줄 알았다. 그런데 정작 HTML을 읽는 단계까지 가지도 못하는 경우가 먼저 나왔다.

퀘이사존은 운영 수집 로그가 찍혔는데, 루리웹은 연결 시간이 초과됐다. 뽐뿌를 추가하려고 확인해 보니 이번엔 `403 Forbidden`이 돌아왔다. 로컬 브라우저에서는 멀쩡히 열리는 게시판이라 더 헷갈렸다.

## HTTP 수집이어서 안 되는 걸까

기존 수집기는 Java의 Jsoup을 쓴다. `Jsoup.connect()`로 페이지를 요청하고, 받은 HTML에서 필요한 항목을 뽑아낸다. 브라우저를 띄우지 않으니 구조가 단순하고 자원도 덜 먹는다.

여기서 말하는 HTTP 수집은 암호화되지 않은 `http://` 접속과는 다르다. 요청 주소는 처음부터 `https://`였다. 뽐뿌의 403은 HTTPS 연결에 실패해서가 아니라, 연결이 된 다음 요청이 거부된 결과다.

루리웹은 증상이 달랐다. OCI에서 DNS 조회까지는 됐지만 TCP 443 연결부터 시간이 초과됐다. 개인 PC에서 같은 주소로 curl을 날리면 200이 나왔다. 서버 방화벽과 OCI Egress 규칙도 뒤져 봤지만 이 연결을 막는 규칙은 없었다.

뽐뿌의 403과 루리웹의 연결 실패가 같은 원인인지는 알 수 없었다. 공통점은 실행 위치에 따라 결과가 갈린다는 것뿐이었다.

## curl 결과만으로 판단하면 안 됐다

처음에는 curl로 접근이 되는지부터 확인했다. 빠르고 간단하지만, 이걸 실제 수집기와 같은 조건으로 여기면 안 됐다.

퀘이사존도 curl에는 Cloudflare 검증 페이지를 돌려줬다. 그런데 그보다 앞선 운영 수집 로그에는 30건을 처리한 기록이 남아 있었다. 두 요청의 시점이 다르긴 하지만, 적어도 curl의 403만 보고 수집기까지 안 된다고 결론 낼 수는 없었다.

그래서 기존 `HtmlFetcher`를 그대로 호출하는 일회성 진단 도구를 만들었다. Spring과 DB는 띄우지 않고 목록만 요청한 뒤 끝나도록 했다. 접근 여부를 확인하려다 운영 데이터를 건드리거나 스케줄러를 중복으로 돌리는 일은 피하고 싶었다.

이렇게 OCI에서 뽐뿌에 요청해도 403이 나왔다. 그제야 기존 Java 수집 방식으로도 접근이 막힌다는 걸 확인했다.

## 도구를 바꾸고 실행 환경도 맞춰 봤다

브라우저 자동화도 비교했다. 개인 PC의 시크릿 창에서는 게시판이 바로 열렸고, 쿠키 없는 새 세션의 Playwright도 창을 띄운 실행에서는 실제 목록을 받아 왔다. 반면 앞서 돌린 headless 테스트는 403이었다. 실행 시점이 서로 달라서 창의 유무만이 원인이라고 못 박기는 어렵다.

다른 공개 핫딜 프로젝트의 구현도 찾아봤다. 브라우저를 직접 띄우는 방식 외에, 브라우저의 통신 특성을 흉내 내는 HTTP 클라이언트를 쓰는 사례가 있었다. Java에도 같은 일을 하는 `impersonator`가 있었다.

여기서도 운영 수집기를 바로 갈아 끼우지는 않았다. 별도 진단 프로젝트에서 고정된 프로필로 한 번만 요청하게 만들었다. 인증서 검증은 그대로 두고, 프록시나 기존 쿠키는 가져오지 않았다. 재시도와 리디렉션도 껐다. 요청 방식의 차이만 보려는 실험이지, 될 때까지 설정을 바꿔 가며 두드리는 수집기가 아니었다.

결과를 정리하면 이렇다.

| 실행 환경 | 요청 방식 | 결과 |
| --- | --- | --- |
| 로컬 PC | Java impersonator | 200, 게시글 링크 후보 42개 |
| OCI | Java impersonator 진단 컨테이너 | 두 번 모두 403 |
| 로컬 Docker Desktop | 같은 진단 코드와 Dockerfile | 200, 게시글 링크 후보 42개 |
| OCI | RSS 주소에 일반 curl 요청 | 403 |

42개는 중복을 뺀 게시글 링크 후보 수다. 링크 후보를 그만큼 찾았다는 뜻이지, 실제 딜을 42건 저장했거나 최신 데이터를 전부 검증했다는 의미는 아니다.

로컬 Docker에서도 성공했으니 Docker를 썼다는 이유만으로 실패한 건 아니었다. 같은 코드가 집에서는 되고 OCI에서는 안 되니, 출발 IP나 네트워크 환경에 따른 제한일 가능성이 커졌다.

물론 "OCI 전체 IP 대역이 차단됐다"고 못 박을 근거는 없었다. 두 환경의 CPU 아키텍처와 이미지 세부 조건이 완전히 같지도 않았고, 사이트 쪽 차단 규칙을 들여다본 것도 아니다. 확인된 건 **지금 내 OCI 환경에서는 거부되고 로컬에서는 성공한다**는 사실 하나였다.

## 코드 수정 대신 수집 위치를 나누기로 했다

여기서부터는 파서를 더 만든다고 풀릴 문제가 아니었다. 그렇다고 포트폴리오용 프로젝트에서 접근이 뚫릴 때까지 서버나 라이브러리를 계속 바꾸는 것도 방향이 아니라고 봤다.

그래서 수집은 노트북 같은 로컬 기기에서 하고, 저장과 조회는 기존 클라우드에 남기기로 했다.

```text
로컬 기기
  목록 수집 · 필요한 상세 조회 · 데이터 정규화
                │
                │ 인증된 HTTPS 전송
                ▼
OCI
  백엔드 API · 중복 확인 · 그룹화 · PostgreSQL
                ▲
                │ 조회 API
                │
Vercel 프론트엔드
  사용자는 기존처럼 웹에서 조회
```

수집할 때 필요한 일은 로컬에서 끝내고 결과만 서버로 보내는 구조다. 방문자의 브라우저가 대신 수집하지도 않고, DB를 외부에 직접 열어 줄 필요도 없다.

로컬 기기가 꺼져도 OCI에 쌓인 데이터는 그대로 남는다. 화면은 계속 볼 수 있고 새 데이터 수집만 멈춘다. 수집이 멈춘 걸 사용자가 알 수 있게 마지막 수집 시각을 보여 주는 것도 같이 생각하고 있다.

다만 **이 글을 쓰는 시점에 끝낸 건 진단 도구와 접근 비교까지다. 로컬 수집 결과를 OCI로 보내는 구조는 방향만 정했고 아직 구현 전이다.** 로컬에서 모든 출처의 전체 수집 과정을 검증하지도 못했다. 뽐뿌는 목록 링크 후보까지, 루리웹은 일반 HTTP 요청 성공까지 확인했다.

## 개인 프로젝트에 맞는 선을 정했다

처음에는 노트북을 계속 켜 둬야 하나 싶었다. 하지만 픽딜은 실시간성을 보장해야 하는 상용 서비스가 아니라 포트폴리오이자 개인용 프로젝트다. 수집 하나 때문에 노트북을 24시간 돌리거나 장비부터 새로 살 이유는 없다고 판단했다.

우선은 로컬 기기를 쓰는 동안만 수집하는 정도로 시작하려 한다. 꺼져 있는 사이 목록에서 밀려난 글은 놓칠 수 있다. 다시 켰을 때 그 구간을 전부 복구하는 기능까지 한꺼번에 만들 생각은 없다. 기존 bootstrap 설정이 있다고 해서 중단 구간이 알아서 메워진다고 믿어서도 안 된다.

대신 실제로 분리할 때는 몇 가지를 챙겨야 한다.

- 로컬 수집기는 DB 없이 뜰 수 있어야 한다.
- 신규 글만 상세 조회하려면 이미 저장된 외부 ID를 서버에 한 번에 물어보는 절차가 필요하다.
- 수신 API에는 인증과 입력 검증을 두고, 기존 공개 쓰기 제한은 유지해야 한다.
- 전송 결과를 못 받아 다시 보내더라도 중복 저장되지 않아야 한다.
- 전송이 실패했을 때 재전송 범위와 데이터 유실 가능성을 미리 정해 둬야 한다.

같은 JAR를 역할별 프로파일로 띄우는 방법도 있지만, 지금처럼 DB에 묶여 있는 수집 흐름을 떼어 내는 작업은 어차피 필요하다. 스케줄러 설정 한 줄 바꾼다고 끝나지 않는다.

## 다음부터 지킬 기준

이 문제에서 가장 크게 배운 건 **HTML을 파싱할 수 있느냐와 운영 서버에서 접근이 되느냐는 별개**라는 점이다. 로컬에서 페이지가 열린다고 배포 환경에서도 수집되리라 믿으면 안 됐다.

다음 출처를 붙일 때는 접근 정책과 제공 피드부터 확인하고, 실제로 돌릴 환경에서 작은 진단을 먼저 하려고 한다. 성공 여부도 상태 코드, 목록 수신, 파싱, 저장을 나눠서 봐야 한다.

로컬 수집으로 방향을 정했다고 사이트의 접근 제한이나 재사용 조건이 사라지지는 않는다. 개인용이라고 자동 수집이 무조건 허용되는 것도 아니다. 공개 화면에 내보낼 데이터 범위와 사이트 정책은 따로 확인해야 한다.

이 선택은 클라우드 접근 문제를 해결했다기보다, 프로젝트 목적에 맞게 책임을 나눈 결정에 가깝다. 실시간으로 모든 딜을 놓치지 않는 것보다, 수집이 멈춰도 이미 모은 데이터는 볼 수 있는 구조를 먼저 만드는 편이 지금은 낫다고 봤다.
